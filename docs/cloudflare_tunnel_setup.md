# Cloudflare Tunnel Setup Guide — DFS Coordinator

This guide walks through every step needed to expose the DFS Coordinator publicly through a Cloudflare Tunnel. The entire setup is done **once** on the Raspberry Pi; no router configuration, no inbound port forwarding.

```
Internet Client
      ↓  HTTPS (Cloudflare cert)
Cloudflare Edge
      ↓  Encrypted tunnel (outbound from Pi)
cloudflared (on Pi)
      ↓  HTTPS to localhost (self-signed cert, TLS verify skipped on loopback)
DFS Coordinator :8000
      ↓  Internal HTTPS (unchanged)
Storage Nodes :8001–8007  (never exposed)
```

> **Cloudflare features used (Free tier only)**
> - Cloudflare Tunnel (`cloudflared`) — Free
> - Cloudflare CDN/Proxy — Free
> - Cloudflare DNS routing for a named hostname — Free
> - Zero Trust tunnel token (up to 50 seats) — Free
>
> **Not used:** Load Balancing, Argo Smart Routing, WAF, Access Policies, paid add-ons.

---

## Prerequisites

| Requirement | Notes |
|---|---|
| Raspberry Pi running the DFS cluster | `python scripts/launch.py` must succeed |
| A domain added to Cloudflare | Any registrar; change nameservers to Cloudflare |
| Cloudflare account (free) | https://dash.cloudflare.com/sign-up |
| Internet access from the Pi | Outbound HTTPS (port 443) must be open |

## Step 1 — Install `cloudflared` on the Raspberry Pi

```bash
# Download the latest ARM64 build (Raspberry Pi 4/5 running 64-bit OS)
curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-arm64 \
     -o /tmp/cloudflared

# For 32-bit Raspberry Pi OS (armhf):
# curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-arm \
#      -o /tmp/cloudflared

sudo install -o root -g root -m 755 /tmp/cloudflared /usr/local/bin/cloudflared

# Verify
cloudflared --version
```

> **Alternative (Debian package):**
> ```bash
> curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo gpg --dearmor -o /usr/share/keyrings/cloudflare-main.gpg
> echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' \
>   | sudo tee /etc/apt/sources.list.d/cloudflared.list
> sudo apt-get update && sudo apt-get install -y cloudflared
> ```

## Step 2 — Authenticate `cloudflared` with Cloudflare

```bash
cloudflared login
```

This opens a browser window. Select the domain you want to use (e.g. `example.com`). Cloudflare places a certificate at `~/.cloudflared/cert.pem`.

> **Headless Pi?** Copy the printed URL and open it on any machine. After authorising, the cert is saved on the Pi automatically.

---

## Step 3 — Create a Named Tunnel

```bash
cloudflared tunnel create dfs-tunnel
```

This creates:
- A tunnel UUID (printed to the terminal, e.g. `a1b2c3d4-...`)
- A credentials file: `~/.cloudflared/<UUID>.json`  ← **keep this secret, never commit it**

Note the UUID — you need it in the next two steps.

---

## Step 4 — Configure the Tunnel

Edit `cloudflare/config.yml` in the project repo:

```yaml
# Replace both <TUNNEL_UUID> occurrences with your actual UUID
tunnel: a1b2c3d4-e5f6-7890-abcd-ef1234567890
credentials-file: /home/pi/.cloudflared/a1b2c3d4-e5f6-7890-abcd-ef1234567890.json

ingress:
  - hostname: dfs.flyinglockin.com    # ← your real hostname
    service: https://127.0.0.1:8000
    originRequest:
      noTLSVerify: true          # coordinator uses a self-signed cert — safe on loopback
      connectTimeout: 10s
      tcpKeepAlive: 30s
      keepAliveConnections: 10
  - service: http_status:404
```

> **Why `noTLSVerify: true`?**
> The DFS Coordinator uses a self-signed TLS certificate (generated by `crypto_utils.py`). This setting tells `cloudflared` to skip certificate verification **only for the loopback connection** (`127.0.0.1`). Traffic between `cloudflared` and Cloudflare's edge is still protected by Cloudflare's own certificate. This is safe and does not affect end-to-end security for Internet clients.

---

## Step 5 — Route a Public Hostname to the Tunnel

```bash
# Creates a CNAME in your Cloudflare DNS: dfs.example.com → <UUID>.cfargotunnel.com
cloudflared tunnel route dns dfs-tunnel dfs.example.com
```

Verify in the Cloudflare dashboard under **DNS** — you should see a CNAME record proxied through Cloudflare (orange cloud ☁️).

---

## Step 6 — Start the DFS Cluster

```bash
cd /home/pi/dfs    # adjust to your actual project directory
source .venv/bin/activate
python scripts/launch.py &
```

Wait for the cluster to be healthy:

```bash
curl -k https://127.0.0.1:8000/cluster
# Should return JSON with node statuses
```

(`-k` skips TLS verification for the self-signed cert on local calls.)

---

## Step 7 — Run the Tunnel (one-shot, for testing)

```bash
cloudflared tunnel --config cloudflare/config.yml run
```

Leave this running in a terminal. Test the public endpoint:

```bash
# From any machine on the Internet:
curl https://dfs.example.com/cluster
```

You should get the same JSON response as from localhost.

## Step 8 — Run as a System Service (production)

### 8a. Create the environment file for the token

```bash
sudo mkdir -p /etc/cloudflared

# Generate the tunnel token (alternative to credentials file):
cloudflared tunnel token dfs-tunnel
# Copy the printed token string

sudo nano /etc/cloudflared/tunnel.env
```

Contents of `/etc/cloudflared/tunnel.env`:

```ini
CF_TUNNEL_TOKEN=eyJhIjoi...paste_your_token_here...
```

```bash
# Restrict permissions so only root can read the token
sudo chmod 600 /etc/cloudflared/tunnel.env
sudo chown root:root /etc/cloudflared/tunnel.env
```

### 8b. Install the systemd service

```bash
# Copy the service unit from the repo
sudo cp cloudflare/cloudflared.service /etc/systemd/system/cloudflared.service

# Reload systemd and enable auto-start on boot
sudo systemctl daemon-reload
sudo systemctl enable cloudflared
sudo systemctl start cloudflared
```

### 8c. Verify service status

```bash
sudo systemctl status cloudflared
# Should show: Active: active (running)

# Follow live logs:
sudo journalctl -u cloudflared -f
```

## Step 9 — Stopping/Starting the Tunnel

| Action | Command |
|---|---|
| Start service | `sudo systemctl start cloudflared` |
| Stop service | `sudo systemctl stop cloudflared` |
| Restart service | `sudo systemctl restart cloudflared` |
| Disable auto-start | `sudo systemctl disable cloudflared` |
| One-shot run (testing) | `cloudflared tunnel --config cloudflare/config.yml run` |
| One-shot with token | `cloudflared tunnel run --token $CF_TUNNEL_TOKEN` |

## Security Notes

| Concern | How it is addressed |
|---|---|
| Storage nodes (8001–8007) | Never appear in `cloudflare/config.yml` ingress rules; catch-all rule returns 404 |
| Tunnel credentials | `.gitignore` blocks `cloudflare/*.json` and `*.token`; credentials file lives in `~/.cloudflared/` |
| Token | Stored in `/etc/cloudflared/tunnel.env` (chmod 600, root-owned), never in code |
| Self-signed cert | `noTLSVerify: true` applies only to the loopback hop; Internet clients receive Cloudflare's cert |
| Pi direct exposure | No ports are opened on the router; `cloudflared` makes outbound connections only |

## Troubleshooting

**`cloudflared` fails to connect**
```bash
# Check that outbound HTTPS is allowed from the Pi:
curl -v https://cloudflare.com
# Check logs:
sudo journalctl -u cloudflared -n 50
```

**Public hostname returns a Cloudflare error**
- Confirm the CNAME was created: `dig dfs.example.com` should show a CNAME to `<UUID>.cfargotunnel.com`
- Confirm `cloudflared` service is running: `sudo systemctl status cloudflared`
- Confirm the DFS cluster is running: `curl -k https://127.0.0.1:8000/cluster`

**`noTLSVerify: true` warning in logs**
- This is expected and safe for loopback origins. No action needed.

**Tunnel works but storage operations fail**
- Storage nodes communicate only with the Coordinator on the Pi's internal network — this is expected and correct. Check `curl -k https://127.0.0.1:8000/cluster` for node statuses.

## Verification

Run the automated verification script after setup:

```bash
# Set your public hostname first
export CF_PUBLIC_HOSTNAME=dfs.example.com

python scripts/verify_cloudflare.py
```

This checks:
1. DFS works normally without Cloudflare
2. Coordinator is reachable locally
3. `cloudflared` process is running
4. Public hostname reaches the Coordinator
5. Upload, download, delete work through the public hostname
6. Storage-node ports are not reachable from the Internet
7. Existing DFS tests pass
